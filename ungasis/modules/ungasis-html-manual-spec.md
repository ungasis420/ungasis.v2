## 1. Purpose of the HTML Manual

The UNGASIS HTML manual should become your personal AI builder operating guide.

| Purpose | Simple meaning | Why it matters |
|---|---|---|
| AI builder guide | Teaches you what to use and when | Reduces confusion when starting projects |
| SOP library | Step-by-step operating procedures | Helps repeat work without starting from zero |
| Glossary | Simple definitions for technical terms | Helps ESL/beginner comprehension |
| Workflow map | Visual flow of how to build projects | Helps you see the full system |
| Prompt library | Copy-paste prompts for tasks | Speeds up repeated work |
| Decision matrix | Tool/stack routing guide | Prevents overbuilding |
| Safety checklist | Data, secrets, approval rules | Prevents costly mistakes |
| Portfolio guide | Shows how to package projects safely | Helps career/credibility growth |
| Monetization guide | Helps test revenue carefully | Prevents charging too early |
| Learning dashboard | Tracks what to learn/practice next | Helps slow, steady progress |
| Source ledger | Tracks verified vs unverified claims | Prevents fake citations and outdated advice |

## 5. HTML Build Requirements

| Requirement | Must-have? | Notes |
|---|---|---|
| Single self-contained HTML file | ✅ Yes | One `.html` file that works locally |
| Offline support | ✅ Yes | Must work with `file://` opening in browser |
| No backend | ✅ Yes | No server required |
| No paid services | ✅ Yes | Must not depend on paid APIs/CDNs |
| No external CDN dependency if possible | ✅ Yes | Prefer inline CSS/JS |
| Responsive layout | ✅ Yes | Works desktop/tablet/mobile |
| Accessible design | ✅ Yes | Good contrast, readable text, keyboard support directionally |
| Print-friendly | ✅ Yes | User can print/save as PDF |
| No secrets/private data | ✅ Yes | No API keys, tokens, private company/client data |
| localStorage only for harmless preferences | ✅ Yes | Theme, sidebar state, section collapse state only |
| Copy buttons | ✅ Yes | For prompt blocks and command blocks |
| Search/filter | ✅ Yes | Search visible sections/content |
| Collapsible sections | ✅ Yes | Reduces overwhelm |
| Light/dark mode | ✅ Yes | User preference only |
| Version footer | ✅ Yes | Version/date/source notes |

## 6. Visual / UX Requirements

### Design style

| Element | Requirement |
|---|---|
| Theme | Premium glassmorphism / dashboard / wiki hybrid |
| Layout | Sidebar navigation + main content + quick cards |
| Cards | Rounded cards, subtle border, soft shadows |
| Typography | Large readable text, simple hierarchy |
| Colors | High contrast, calm, not too many colors |
| Icons | Emoji or inline SVG only; no paid icon dependency |
| Motion | Minimal and useful only |
| Mobile | Sidebar collapses; content remains readable |

### Preferred visual language

```text
Glassmorphism feel:
- translucent panels
- soft borders
- subtle blur
- modern dashboard cards
- clear section dividers
```

### Suggested CSS direction

```css
/* Theme tokens example only; final file may adjust values safely. */
:root {
  --bg: #0f172a;
  --panel: rgba(255, 255, 255, 0.04);
  --border: rgba(255, 255, 255, 0.10);
  --text: #e5e7eb;
  --muted: #94a3b8;
  --accent: #38bdf8;
}
```

> Note: For your web-app projects, you often prefer Tailwind-style classes like `border-white/10`, `bg-white/[0.04]`, and `backdrop-blur-xl`. For a single-file offline HTML manual, equivalent plain CSS variables/classes are safer.

## 9. Security and Privacy Requirements

### Hard no

The HTML manual must never include:
- API keys
- passwords
- tokens
- connection strings
- private certificates
- service-role keys
- real client data
- confidential work data
- regulated personal data
- hidden tracking scripts
- external analytics by default

### localStorage rule

Allowed:
- theme preference
- sidebar collapsed state
- completed checklist state if harmless
- last opened section if harmless

Not allowed:
- secrets
- private notes
- company data
- personal sensitive data
- user identities
- payment data

## 10. Build Strategy — Chunked Approach

Build the HTML manual in safe chunks.

| Chunk | Output | Why |
|---|---|---|
| 1. Skeleton | HTML layout, sidebar, header, footer | Creates structure first |
| 2. Core styles | Theme tokens, cards, responsive layout | Makes it readable early |
| 3. Core JS | Search, copy buttons, collapsibles, theme toggle | Adds usefulness |
| 4. Must-have sections | Home, safety, lifecycle, matrix, lanes | Creates useful v1 |
| 5. Prompt/SOP starter | Copyable prompt and SOP blocks | Makes it operational |
| 6. Source ledger/evolution | Source table and changelog | Adds trust and traceability |
| 7. Print/mobile QA | Print CSS and responsive fixes | Makes it practical |
| 8. Polish pass | Accessibility, spacing, hierarchy | Makes it pleasant to use |

## 19. “Do Not Build Yet” Reminder

For the first HTML manual, do not build:

| Feature | Status | Why |
|---|---|---|
| User login | ⏸️ Deferred | Not needed for local manual |
| Database | ⏸️ Deferred | Static HTML is enough |
| Cloud backend | ⏸️ Deferred | Adds cost/complexity |
| Payment system | ⏸️ Deferred | Manual is not a validated SaaS yet |
| Multi-user permissions | ⏸️ Deferred | Local/private v1 first |
| AI API integration | 📐 Blueprint | Useful later, not needed for v1 |
| Analytics tracking | ⏸️ Deferred | Avoid privacy risk in local manual |
| Complex CMS | ⏸️ Deferred | Markdown/source modules are enough |

## 22. Final Rule

> Build the manual like a tool, not a museum.

A good v1 manual should help you do work immediately:
- choose a tool
- copy a prompt
- follow an SOP
- check safety
- find a term
- decide next action

If it looks beautiful but does not help you act, simplify it.
