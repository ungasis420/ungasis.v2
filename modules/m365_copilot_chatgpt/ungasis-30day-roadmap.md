# UNGASIS Content Module: 30-Day Roadmap + Next 7 Actions

**File:** `ungasis-30day-roadmap.md`  
**Purpose:** A beginner-friendly 30-day roadmap for validating, prototyping, building, testing, deploying, and carefully preparing a monetization experiment for a solopreneur app or UNGASIS-powered project.  
**Audience:** Mel John Dimat — beginner, ESL, visual learner, $0 budget, AI-assisted solopreneur builder.  
**Mode:** Deep / Roadmap Module.  

> 🍳 **Simple analogy:** This roadmap is like opening a food stall before a restaurant.  
> First, check if people are hungry.  
> Then cook a small sample.  
> Then improve the recipe.  
> Only after people want it, consider selling.

---

## 1. Your 7 Starter Actions

Do these before trying to build a big app.

| # | Action | Output | Why it matters |
|---:|---|---|---|
| 1 | Create a Notion, OneNote, Word, or Markdown page called `My App Ideas` | One idea page | Gives your ideas one home |
| 2 | Write 3 app ideas using the one-sentence formula | 3 idea drafts | Prevents falling in love with only one idea too early |
| 3 | Pick the idea with the strongest pain and easiest user access | 1 chosen idea | Focus beats scattered effort |
| 4 | Create a 7-question validation form | Survey link | Lets real people tell you if the pain exists |
| 5 | Share it with 10 people or communities | Outreach list + responses | Real feedback beats guessing |
| 6 | Sketch 3 screens on paper or Excalidraw | Simple wireframes | Shows the app flow before coding |
| 7 | Use Bolt, Google AI Studio, Lovable, v0, Figma, or another prototype tool with fake data | Rough clickable prototype | Lets users react to something visible |

### Do not build yet

Do **not** build these at the start:

| Do not build yet | Why |
|---|---|
| Payment system | No proof people will pay yet |
| Admin panel | Usually not needed for first validation |
| Complex dashboard | Can distract from the main user pain |
| Multi-user team features | Adds complexity too early |
| Mobile app store release | Too much setup before validation |
| AI agent automation | Risky before workflow is proven |
| Full SaaS backend | Too heavy before real demand |

## 2. One-Sentence Idea Formula

Use this for each idea:

```text
I help [specific user] who struggles with [specific pain]
achieve [specific result] without [current frustration].
```

### Example

```text
I help solo tutors who lose student lesson notes
organize follow-up actions without searching across notebooks and chats.
```

---

## 3. 30-Day Roadmap Overview

| Week | Theme | Main goal | Build level |
|---|---|---|---|
| Week 1 | Validate | Prove the pain is real | No-code / docs only |
| Week 2 | Prototype and learn | Make a clickable rough version | Prototype only |
| Week 3 | Build MVP | Build the smallest functional version | One core workflow |
| Week 4 | Test, deploy, monetize carefully | Test with users and decide next move | Private/public only if ready |

### Golden rule

```text
Do not build a big product until people prove the problem matters.
```

---

# Week 1 — Validate

**Goal:** Confirm the problem is real before building.

| Day | Action | Output |
|---:|---|---|
| 1 | Write 3 app ideas | Idea list |
| 2 | Pick 1 user + pain | Problem statement |
| 3 | Create Tally, Microsoft Forms, or Google Forms survey | Validation form |
| 4 | Message 10 people | Outreach list |
| 5 | Analyze responses | Go / pivot / kill decision |
| 6 | Write MVP scope | 3 features + not-building list |
| 7 | Sketch screens | 3-5 wireframes |

## Week 1 Checklist

| Check | Done? |
|---|---|
| I know the exact target user | ☐ |
| I know the painful problem | ☐ |
| I know how they solve it today | ☐ |
| I contacted real people | ☐ |
| I have survey/interview feedback | ☐ |
| I made a go / pivot / kill decision | ☐ |
| I wrote a clear not-building list | ☐ |

### Week 1 do-not-build reminder

Do not build the app yet.  
Your job this week is to check if the problem is worth solving.

---

# Week 2 — Prototype and Learn

**Goal:** Create a rough prototype and learn enough tooling to continue safely.

| Day | Action | Output |
|---:|---|---|
| 8 | Build with Bolt / Google AI Studio / Lovable / v0 / Figma | Clickable prototype |
| 9 | Show 3-5 people | Feedback notes |
| 10 | Improve prototype | Version 2 prototype |
| 11 | Create GitHub repo if code is involved | Project safe box |
| 12 | Create README / PROJECT_WORKFLOW | Project docs |
| 13 | Learn Supabase or simple data storage basics if needed | One test table or data plan |
| 14 | Learn deploy basics | Simple public or private test link |

## Week 2 Checklist

| Check | Done? |
|---|---|
| Prototype uses fake/demo data only | ☐ |
| Main user flow can be clicked | ☐ |
| 3-5 people saw it | ☐ |
| Feedback is saved | ☐ |
| GitHub repo exists if code is involved | ☐ |
| README exists | ☐ |
| PROJECT_WORKFLOW exists | ☐ |
| No secrets are in the repo | ☐ |

### Week 2 do-not-build reminder

Do not add payments, complex auth, analytics dashboards, or automation yet.  
This week is for learning and feedback.

---

# Week 3 — Build MVP

**Goal:** Build the smallest functional version with one useful workflow.

| Day | Action | Output |
|---:|---|---|
| 15 | Finalize data model | Tables / fields |
| 16 | Build screen 1 | First page |
| 17 | Build screen 2 | Core workflow start |
| 18 | Build screen 3 | Result / detail page |
| 19 | Connect save/read data | Functional app |
| 20 | Add basic auth only if needed | Login flow |
| 21 | Run manual test checklist | Bug list |

## Week 3 Checklist

| Check | Done? |
|---|---|
| MVP has one target user | ☐ |
| MVP has one main workflow | ☐ |
| MVP has max 3 must-have features | ☐ |
| Data save/read works if needed | ☐ |
| Auth is added only if needed | ☐ |
| Main flow works on mobile size | ☐ |
| Manual test checklist exists | ☐ |
| Bugs are listed clearly | ☐ |

### Week 3 do-not-build reminder

Do not build every feature users mention.  
Only fix what blocks the main workflow.

---

# Week 4 — Test, Deploy, Monetize Carefully

**Goal:** Test with users, stabilize, and decide whether monetization is justified.

| Day | Action | Output |
|---:|---|---|
| 22 | Fix top bugs | Stable MVP |
| 23 | Deploy private test | Test link |
| 24 | Add feedback form | Feedback loop |
| 25 | Invite 5-10 testers | Real usage |
| 26 | Add monitoring if public | Sentry / UptimeRobot / simple checks |
| 27 | Decide monetization test | Offer hypothesis |
| 28 | Add payment link only if justified | Paid pilot option |
| 29 | Review metrics | Continue / pivot / kill decision |
| 30 | Write next sprint plan | Next 7 actions |

## Week 4 Checklist

| Check | Done? |
|---|---|
| Top bugs fixed | ☐ |
| Test link works | ☐ |
| Feedback form exists | ☐ |
| Testers invited | ☐ |
| Privacy note exists if collecting data | ☐ |
| Support/contact path exists | ☐ |
| Monitoring exists if public | ☐ |
| Monetization is based on evidence, not excitement | ☐ |
| Continue / pivot / kill decision made | ☐ |

### Week 4 do-not-build reminder

Do not add a payment link just because the app exists.  
Only add payment if users show strong value or willingness to pay.

## 4. Stage Gates

Use these gates before moving forward.

| Gate | Pass condition | If not passed |
|---|---|---|
| Validation gate | Real people confirm the pain | Return to idea selection |
| Prototype gate | Users understand the flow | Improve prototype |
| MVP gate | One core workflow works | Fix before adding features |
| Public gate | Privacy, support, rollback, and safety are ready | Stay private |
| Monetization gate | Users show willingness to pay | Use waitlist or free beta first |

---

## 5. Metrics to Track

Start with only five metrics.

| Metric | Simple meaning | Tool option |
|---|---|---|
| `visited_landing` | User saw the page | Analytics / simple counter |
| `signed_up` | User joined or created account | Form / auth / list |
| `completed_core_action` | User got first value | Manual tracking or analytics |
| `returned_later` | User came back | Analytics / usage log |
| `clicked_pricing_or_paid` | User showed payment signal | Link click / payment dashboard |

### Beginner warning

Do not build a big analytics system before users exist.

## 9. Anti-Bloat Rules for the 30 Days

| Temptation | Decision |
|---|---|
| Add login | ⏸️ Deferred |
| Add database | ⏸️ Deferred unless needed |
| Add payments | ⏸️ Deferred until value proven |
| Add AI agent | 📐 Blueprint until content base is stable |
| Add Power Platform version | 📐 Blueprint after HTML/manual version works |
| Add SaaS architecture | ⏸️ Deferred |
| Add complex analytics | ⏸️ Deferred until real users exist |

---

## 10. Human Approval Gates

Before doing any of these, stop and review:

| Action | Approval needed? | Why |
|---|---|---|
| Publish public link | Yes | Could expose private content |
| Add payment link | Yes | Money creates obligations |
| Email users | Yes | Affects real people |
| Collect personal data | Yes | Privacy responsibility |
| Use company/client data | Yes | Must follow approved environment and policy |
| Automate sending/deleting/updating | Yes | Risk of mistakes |
| Change permissions | Yes | Security risk |

---

## 11. Final 30-Day Rule

> The goal is not to build the biggest thing.  
> The goal is to prove the next smallest useful thing.

```text
Validate before building.
Prototype before coding.
Test before launching.
Learn before monetizing.
Document before scaling.
```
